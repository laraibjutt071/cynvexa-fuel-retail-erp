# Remaining Risks (Phase 7 production-readiness review)

Ranked by what would actually hurt in production, not by how interesting the finding is. Each item says what was found, what (if anything) was fixed, and what's still open. Cross-references to `docs/ASSUMPTIONS.md` are for the full technical reasoning; this file is the prioritized summary.

## Would block a real multi-replica production launch

1. **Local-disk evidence storage** (`app/core/storage.py`). Not fixed - already a known Phase B limitation, re-confirmed still true. Breaks silently (no error, just inconsistent visibility) with more than one backend replica. Fix: object storage (S3 or equivalent); the schema already supports the swap (`Attachment.storage_backend`). `docs/ASSUMPTIONS.md` #31.
2. **Migration-on-boot races with more than one replica** (`docker-entrypoint.sh`). Not changed in code (would have broken the established single-instance dev convenience documented since Phase A). Documented production workaround in `docs/DEPLOYMENT.md`: run migrations as a separate step before scaling up. `docs/ASSUMPTIONS.md` #32.
3. **Login rate limiter is single-instance only** (`app/core/rate_limit.py`, added this phase). Real protection for one replica; provides none of its intended protection once requests are split across replicas with independent in-memory counters. Fix: move to a shared store (Redis). `docs/ASSUMPTIONS.md` #30.

None of these are subtle - they're all the same underlying pattern (in-process state that doesn't generalize to N processes) surfacing in three different places. **If the production plan is a single backend replica, none of these three block launch.** They block *scaling past one replica*, which is a real near-term risk for a growing deployment, not a theoretical one.

## Real, fixed this phase (verify they stay fixed)

4. **29 missing database indexes**, including the single hottest query in the app (`get_book_stock`, run on every capacity check, shift approval, and variance report). Fixed via migration `eca78cafd252`; measured 0.28ms vs 11.5ms (≈40x) at a realistic 200k-row/500-tank synthetic scale, rolled back after measuring. Regression risk: a future model change that adds a new hot filter column won't automatically get an index - this needs the same "grep every `.where(X.*_id ==`" review repeated periodically, not a one-time fix.
5. **Three dependencies with known CVEs**: `pyjwt` 2.10.1→2.15.1, `python-multipart` 0.0.17→0.0.32, and `starlette` 0.41.3→0.47.2 (pulled in via a `fastapi` 0.115.6→0.128.0 bump, chosen as the smallest version jump that resolves the starlette range rather than jumping to the latest fastapi, to limit the blast radius of a dependency upgrade done under time pressure). Verified via `pip-audit` before and after; full backend test suite (176 tests) passes on the upgraded versions. `npm audit` on the frontend found 0 vulnerabilities - no change needed there.
6. **File upload trusted the client's Content-Type header with no verification against actual bytes** - a textbook disguised-upload vector. Fixed: real magic-byte signature checking for all 4 allowed types, plus chunked reads with an early size-limit abort (previously the whole body was buffered into memory before the size check ran). This is the only endpoint that accepts arbitrary binary uploads in the whole app, so this was a complete fix for the current surface, not a partial one - but if a future phase adds another upload endpoint, it needs to go through `app/core/storage.py::save_evidence_upload` (or an equivalent that applies the same checks), not a new one-off implementation.
7. **Zero test coverage on the file-upload endpoint** - the endpoint existed since Phase B with no automated test at all. Fixed: 8 new tests (`tests/test_attachments.py`) covering valid uploads, rejected content-type, the new disguised-content rejection, empty/oversized files, path-traversal filename handling, and the permission boundary.
8. **No brute-force protection on login.** Fixed within the single-instance scope described above (item 3) - 10 attempts / 5 minutes per email+IP, reset on success. 5 new tests (`tests/test_rate_limit.py`).
9. **Containers ran as root.** Fixed - both images now run as a non-root user, verified via `whoami` in the running containers. Found one real consequence while verifying: the pre-existing `cynvexa_uploads` Docker volume (populated under the old root-owned image) wasn't automatically re-owned by the new non-root user, and had to be `chown`'d once by hand. **If you've run this app's backend container before Phase 7 and have a populated uploads volume, you will hit the same issue on upgrade** - the fix is a one-time `docker compose exec -u root backend chown -R appuser:appuser /app/uploads` before scaling it means one container up with the new image.
10. **`COPY . .` in both Dockerfiles with no `.dockerignore`** - could bake a developer's local `.env`, `.venv`, `node_modules`, or `.git` into an image layer. Fixed - both Dockerfiles now have a `.dockerignore`.

## Found, deliberately not fixed this phase (with the reasoning for why not)

11. **No server-side idempotency key for pure-create endpoints** (tenders, cash movements, expenses, supplier payments, credit-customer collections, inventory movements). A double-click or retried network request creates two rows, not one. This is real and matches exactly what "duplicate submission protection" review items usually mean in production financial systems - it was found, not missed. It was **not** built this phase because doing it properly (an `Idempotency-Key` header, a dedup table, and rewiring roughly six endpoints to use it without breaking FastAPI's automatic response serialization) is a feature-sized change, and building a partial/rushed version under the time pressure of an already-large review pass risked shipping something that looks fixed but isn't reliable. Instead: added a client-side submit-button guard to the one new UI form that creates a financial/stock record (inventory movements), which stops the common real-world cause (double-click), and documented the complete fix clearly so it isn't silently forgotten. `docs/ASSUMPTIONS.md` #33.
12. **Inventory valuation / COGS is not computed** - not a Phase 7 finding specifically (inherited from Phase 6), re-confirmed still true and still open. `docs/ASSUMPTIONS.md` #28.

## Reviewed and found adequate (no action needed)

- **Authentication/authorization structure**: every mutating endpoint goes through one shared `require_permission` dependency resolving org/station scope from the URL path only (never the request body) - this was the exact design the Phase A QA pass hardened, and it held up under this review without new findings.
- **Transaction safety**: `get_db()`'s `async with AsyncSessionLocal()` pattern rolls back on any unhandled exception automatically; every state-transition endpoint locks its row (`SELECT ... FOR UPDATE`) before checking status, verified by real concurrent-connection tests (`asyncio.gather` against separate DB sessions) in earlier phases, not just read for this review.
- **Connection pooling**: already configured for a reasonable single-instance load (`pool_size=10, max_overflow=20, pool_pre_ping=True, pool_recycle=1800`); the only caveat is the multi-replica multiplication noted in `docs/DEPLOYMENT.md`.
- **Structured logging & health checks**: already JSON-formatted in staging/production, already a correct liveness (`/health`, no DB touch) vs. readiness (`/ready`, does touch the DB) split. No changes needed.
- **Secret management**: `JWT_SECRET_KEY` has no code-level default (app refuses to start without one); secure-cookie flag already tied to `ENV=production`. No changes needed beyond the `.dockerignore` fix above.

## Not evaluated (no credentials/environment available)

- **Actual cloud provider deployment** - no deployment credentials were available in this environment, so nothing was deployed to a real cloud target. `docs/DEPLOYMENT.md` describes what's needed; none of it has been run against AWS/GCP/Azure/etc.
- **TLS/HTTPS termination end-to-end** - no reverse proxy/load balancer was available to test against.
- **Production-scale load testing** - the index benchmark above used synthetic data at one realistic shape (200k rows/500 tanks) measured via `EXPLAIN ANALYZE`, which is real measured evidence for that specific query, not a load test of the whole API under concurrent traffic. No formal load-testing tool (k6, Locust, etc.) was run.
- **Accessibility beyond a spot check**: added `role="tab"`/`aria-selected` to the dashboard's own tab controls (a real, if small, fix - and the one that broke and then fixed the Playwright selectors that assumed `role="button"`, which is worth knowing if you touch those tests again). Did not do a full WCAG audit (color contrast, full keyboard-nav trace, screen-reader pass) of the whole frontend - that's a real gap, not something to claim as "reviewed" based on one fix.

## UI/UX upgrade pass (daily operations workspace, owner dashboard redesign)

Real defects found and fixed while building this, by actually running the app end to end rather than trusting the code read:

1. **A single-day shift lookup silently returned nothing near local midnight for a station whose configured timezone differs from the server's.** `business_date` filtering in `app/api/shifts.py::list_shifts` now resolves the day boundary in `Station.timezone` (defaults to UTC), not hardcoded UTC - with a fallback to UTC if the configured timezone string isn't a real IANA zone. Found via a real end-to-end test, not a code read; see `docs/ASSUMPTIONS.md` #35.
2. **The frontend's own "today" computed the *browser's* local calendar date, not the station's.** Three separate `toISOString().slice(0,10)` call sites (`lib/date.ts`, the Daily Entry page, the Today's Overview page, `DateRangeFilter`) have been consolidated into `lib/date.ts`, with `stationDateIso(timezone)` used everywhere a station's own business day matters (the plain `localDateIso`/`localDateDaysAgoIso` remain for report date-range defaults, which are not station-specific).
3. **`zoneinfo` had no IANA tzdata source at all on this Windows dev machine** (`ModuleNotFoundError: No module named 'tzdata'`), which would have silently degraded every station-timezone lookup to UTC with no error. Added the `tzdata` PyPI package to `requirements.txt` - pure data, no code, makes the lookup work on any host regardless of what OS-level tzdata it does or doesn't ship.
4. **The Daily Entry workspace had no way to enter a tank's closing dip reading at all** - the "Opening stock" card only ever rendered an opening-dip input. Found because the real end-to-end test's "close the shift" step failed with the exact backend validation message naming the missing reading, not because anyone read the component and spotted the gap. Fixed by adding the closing-dip column.
5. **Starting a new Daily Entry for a past, empty date silently created a shift dated "today" instead** - there is no way to backdate a shift's `opened_at` on the backend (by design - see `docs/ASSUMPTIONS.md` #36), so the create would silently succeed while landing on the wrong day, leaving the UI stuck showing "nothing recorded" even though a (wrongly-dated) shift now existed. Fixed by only offering "Start today's entry" when the selected date is actually today; a past empty date now explains that a missing day is a correction, not a new entry.

Deliberately not fixed/built this phase - triaged, not missed:

- **Purchases page** is a first, functional pass (record a delivery, record the unload reading, approve) reusing the existing tanker-receipt API - it does not yet show duplicate-delivery-document warnings or ordered-vs-invoiced-vs-received variance callouts beyond what the approval step's own `tank_gain_quantity` figure already surfaces.
- **A local port conflict** was hit and worked around *for testing only*: another process on this machine (unrelated to this project) already holds the documented ports 3000 and 8000 at various points, which blocked `docker compose up` on the standard ports and caused CORS/networking confusion until diagnosed. `docker-compose.yml` and `backend/.env` were restored to the documented 3000/8000 after verification; if that conflict recurs, it is an environment condition (something else running on this machine), not a defect in this app, and the fix is to stop whatever else is using those ports or run this stack with different host ports via a local `docker-compose.override.yml`.

### Second pass (premium black/blue theme, i18n, charts, Users & Settings) - see `docs/UX_UPGRADE_PLAN.md` for the full record

Real defects found and fixed, again by actually running the app rather than trusting a code read:

6. **`text-ink`, `bg-surface-muted`, `border-border` and several other design tokens generated no CSS at all.** They were declared on `:root` but never re-declared inside Tailwind v4's `@theme` block, which is the only place it looks to generate utility classes. Confirmed by grepping the compiled production CSS for the missing class names before and after the fix - this had been silently broken since the original design-system pass, affecting `Button`, `Field`, `Badge`, `Toast`, `EmptyState`, `AppShell`, and multiple pages.
7. **Two `useLanguage()` additions would have shadowed their own translate function** - `ReadingsSection.tsx` and `SalesSection.tsx` both had a `.map((t) => ...)` loop variable already named `t`, the same name the i18n hook returns. Caught by reading the file before editing, not by the type checker; fixed by renaming the loop variables.
8. **A translation added for an already-tested English label didn't match the original string exactly** (`cash.actualPhysicalCash` was written as "Actual physical cash counted" instead of the existing "Actual cash counted"), which broke `daily-entry.spec.ts`'s exact-label Playwright selector. Caught by actually re-running the full e2e suite after the change, not by assuming a paraphrase was safe.
9. **The "Users & Settings" sidebar link had no permission gate at all**, unlike every other nav item - it would have shown (and linked to a now-real page) for a user without `user:read`. Fixed by gating it on `can(["user:read"])`, matching the pattern already used everywhere else in `AppShell.tsx`.
10. **There was no way to read a user's existing role assignments** - only `POST`/`DELETE` existed for a `UserStationRole`, no `GET`. This made a real Users & Settings page impossible to build without a backend change. Added `GET /organizations/{id}/users/{user_id}/roles` (read-only, reuses the existing `USER_READ` permission and org-membership scoping) with two new passing tests in `backend/tests/test_rbac.py`.

Built this pass: full English/Roman Urdu translation of the sidebar, login, Today's Overview, and the entire Daily Entry workflow (client-side-only persistence - see `docs/ASSUMPTIONS.md` #37); 6 real-data charts (`recharts`) across the dashboard and report tabs; a step-progress indicator and contextual help text on the Daily Entry workflow; a working Users & Settings page (user list, create user, assign/revoke roles, change password, session management); restrained CSS-only animations respecting `prefers-reduced-motion`.

Deliberately not built this pass - triaged, not missed:

- **Revenue-by-payment-method chart** - no report endpoint aggregates tenders by payment method across a date range yet; flagged rather than built as an ad-hoc N+1 fetch across every shift in range.
- **Translating the older Phase-6 report tabs** (org/station dashboard's Suppliers/Credit/Audit/Expenses/Reports tabs) - the Daily Entry workflow and main nav were prioritized as the higher-traffic, non-technical-user-facing surface.
- **Onboarding tour, draft/autosave on Daily Entry forms, a dedicated WCAG audit** - same honest gaps as before, not newly claimed as done.
