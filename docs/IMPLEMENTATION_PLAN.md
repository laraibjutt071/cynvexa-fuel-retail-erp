# Implementation Plan

Phases map to the blueprint's priority order (Phase A–G). Each phase is implemented, tested and reported before the next starts. "Phase 1" below is Phase A.

## Phase A — Foundation (current phase)

**Scope:** application structure, database + migrations, authentication, authorization/roles, organization + station configuration, audit logging, error handling, automated tests.

**Out of scope here (later phases):** anything fuel/shift/cash/stock-specific. Phase A exists to make every later phase's "who can do this, to which station, and is it logged" question already answered.

**Acceptance criteria for Phase 1:**
1. A new user cannot be created with a duplicate email; passwords are hashed (argon2), never stored or logged in plaintext.
2. Login issues a short-lived access token and a rotating refresh token (HttpOnly cookie); an invalid/expired token is rejected with a safe 401, no stack trace or internals leaked.
3. A user assigned a role at Station X cannot read or write Station Y's data, even with a valid token (isolation enforced at the query layer, verified by a test that asserts a 403/404, not just that the UI hides the option).
4. Every permission check goes through one shared dependency (`require_permission`); there is no endpoint that skips it.
5. Creating/updating/deactivating an Organization, Station, or User writes an `AuditLog` row with actor, action, entity id, timestamp, and (for updates) before/after values, in the same transaction as the change.
6. Unhandled exceptions return a generic safe error body in production mode (no traceback, no SQL, no secrets); FastAPI debug/reload is off when `ENV=production`.
7. `pytest` passes for: password hashing round-trip, login success/failure, token expiry rejection, cross-station access denial, audit log write-on-mutation, and org/station CRUD validation.
8. The app boots from `docker-compose up` with Postgres, runs Alembic migrations on startup (not by hand), and exposes a `/health` and `/ready` endpoint that actually checks the DB connection.

## Phase B — Fuel Operations
Fuel grades, tanks + safe capacity, dispensers/nozzles, effective-dated prices, purchase orders/allocations, tanker receipts (document/accepted/payable quantity kept distinct per `docs/ASSUMPTIONS.md` #1), opening/closing tank readings, append-only book-stock ledger, physical observations, variance investigations.
**Acceptance focus:** book stock is reproducible purely from the ledger; a physical reading never overwrites it; receipt tolerance and evidence rules are per-station config, not hardcoded.

**Scoped out of this pass, carried forward:** fuel purchase orders/allocations (the blueprint's §4 "order/allocation" phase) and formal stock variance *investigation* records (a dedicated workflow for an unresolved physical-vs-book discrepancy, distinct from the receipt variance already computed). Both are real blueprint items not covered by the user's Phase B request, which asked specifically for station config, fuel grades, tanks, dispensers, nozzles, prices, suppliers and the receipt workflow — not for purchasing or variance-investigation on top of it.

## Phase C — Shift Operations
Shift open/close, opening/closing tank + nozzle readings, exceptional litres/test/calibration, mid-shift price-change boundary readings, gross dispensed quantity, stock variance reporting, submission/approval workflow.
**Acceptance focus:** gross litres = closing − opening, reproducible and rejected if negative without an approved meter-event; mid-shift price-change boundary readings follow the per-station rule in `docs/ASSUMPTIONS.md` #6.

**Scoped out of this pass, carried forward:** expected revenue (there is no tender/cash capture yet to reconcile against - that's Phase D) and any reopen/correction workflow for a closed or approved shift (`docs/ASSUMPTIONS.md` #7/#18). The user's Phase C request asked specifically for readings, shift open/close, exceptional litres, test/calibration and stock variance reporting, plus explicit handling for meter events and price changes - not for revenue math on top of it.

## Phase D — Financial Reconciliation
Cash/card/digital/credit capture, cash expenses, deposits/safe transfers, refunds, expected-vs-actual, shortage/excess investigation, reviewer approval.
**Acceptance focus:** a shortage can never be hidden by editing fuel quantity or expected revenue — structurally separate fields, separate approval.

**Scoped out of this pass, carried forward:** full credit-customer features (limits, balance, ageing, statements - `CreditCustomer` is a deliberate minimal stub here, see `docs/ASSUMPTIONS.md` #22) and general (non-shift) expense tracking. Both are Phase E's "Supporting Operations" scope, not asked for in this phase's explicit request.

## Phase E — Supporting Operations
Credit customers/balances, expenses, shop/lubricant inventory, inventory movements. (Suppliers and the `Attachment` evidence model were pulled forward into Phase B, since the tanker receipt workflow needed both.)

## Phase F — Management
Owner dashboard, daily sales/shift/fuel-stock/variance/cash-reconciliation reports, supplier/customer balances, audit history, CSV/spreadsheet export.

## Phase G — Production Readiness
Security hardening pass, concurrency/load testing on shift submission and reconciliation, backup/recovery drill, error monitoring, deployment to a real environment, production verification, user documentation.

### Phase A addendum (2026-10-26, independent QA pass)

An adversarial re-review of the actual code (not a re-check of prior claims) found four real defects, all fixed and covered by new regression tests in `backend/tests/test_qa_defects.py`. Reproduction tests were written and run against the *unfixed* code first to confirm each was real, then again after the fix.

1. **Privilege escalation in role granting/revocation (the significant one).** `POST/DELETE /organizations/{org}/users/{user}/roles[/...]` relied solely on `require_permission(USER_ASSIGN_ROLE)`, which resolves scope from the URL only (organization-level - that route has no `station_id` path segment). But the scope being *granted* comes from the request body (`payload.station_id`). Net effect: a user holding `USER_ASSIGN_ROLE` at a single station (not org-wide) could grant **another user an org-wide role** - privilege escalation. Not exploitable through the seeded roles today (only "Owner", which is already org-wide, carries this permission), but it is a latent vulnerability in the authorization primitive itself, and Phase B/C/D will add more roles. Reproduced with a custom role granting only `USER_ASSIGN_ROLE` scoped to one station: before the fix, that actor successfully granted the *Owner* role (org-wide) to a third user (`201 Created`). Fixed with a new, deliberately stricter function, `app/core/permissions.py::actor_can_grant_scope` (cannot reuse `user_has_permission` - see its docstring for why), applied to both grant and revoke. Added a positive-path test proving the fix does not block legitimate station-scoped delegation or org-wide Owner actions.
2. **Misleading error on a non-existent organization.** `create_station` (and `assign_role`) had no explicit check that `organization_id` exists; a bad id would hit the database's foreign-key constraint, which was caught by a generic `except IntegrityError` that always reported "a station with this code already exists" - wrong and misleading when the real problem is "no such organization." Only reachable via the superuser bypass (ordinary users can't reference an org they hold no role in, since that role itself has a foreign key to the organization). Reproduced: superuser POSTing a station to a random UUID got `409 Conflict` instead of `404`. Fixed with a shared `app/api/common.py::get_organization_or_404`, called before any insert in `stations.create_station`, `users.create_user`, and `users.assign_role`.
3. **Wrong status code for malformed input.** `require_permission` raised `PermissionDeniedError` (403) when `organization_id`/`station_id` in the URL failed `uuid.UUID(...)` parsing - conflating "malformed request" with "access denied." Reproduced: `GET /organizations/not-a-uuid` with a valid token returned `403`. Fixed to raise `ValidationFailedError` (422) instead.
4. **AppErrors with a real underlying cause were never logged server-side.** The structured-logging work earlier in Phase A only logged truly unhandled exceptions; an `AppError` like `/ready`'s `ServiceUnavailableError` (raised `from` a real asyncpg connection failure) produced the correct safe response to the client but left no trace in the server log of *why* - the access-log line showed the 503 status but not the cause. Reproduced by pointing `DATABASE_URL` at a closed port and inspecting the log: only the generic access-log line appeared, no exception detail. Fixed: `app_error_handler` now logs (with the original traceback via `exc_info=exc.__cause__`) specifically when the `AppError` was raised with a chained cause, while leaving routine 4xx errors (404/409/403 raised directly, no cause) unlogged to avoid noise. Re-verified by reproducing the same bad-`DATABASE_URL` scenario: the server log now shows the full asyncpg connection traceback while the HTTP response is still just `{"detail": "Database is not reachable."}`.

**Also checked and found correct (no defect):** FastAPI's own `RequestValidationError` handling (malformed JSON, missing required fields) is not shadowed by the app's generic `Exception` handler - verified by sending literally malformed JSON and a body missing required fields, both returned proper field-level `422`s. `/health` stays `200` and `/ready` correctly returns `503` (not a crash) when the database is unreachable.

**Regression run after all four fixes:** `pytest tests/` → **37 passed, 0 failed** (32 original + 5 new: 2 negative/reproduction, 1 status-code, 2 positive-path). Frontend `npm run lint`, `npx tsc --noEmit`, and `npm run build` re-run clean with no changes needed on the frontend side.

**Documentation updated to match:** `ARCHITECTURE.md` §7 now documents the grant-scope invariant explicitly, since it's a rule future phases must keep respecting when new roles are added.

### Phase A addendum (2026-10-26, auth/RBAC/audit hardening pass)

Explicitly re-scoped to deepen authentication, user management, RBAC, org/station-level permissions, session handling, and audit logging — fuel operations intentionally still out of scope. Inspected the current implementation first (every route's dependency chain, the seeded role→permission map for least-privilege) rather than re-describing what Phase A already had.

**Gaps found and closed:**
1. **Cross-station audit leakage.** `AuditLog` had no `station_id` column, so `GET /organizations/{id}/audit-log` returned every station's events to anyone with `AUDIT_READ` anywhere in the org — including a role deliberately scoped to just one station. Added `AuditLog.station_id` (migration `7f2f05f5b92b`), populated it on every station-related audit write (station create/update, role grant/revoke when station-scoped), and added `app/core/permissions.py::get_station_visibility_scope` + filtering in the audit router. Verified with a reproduction test: a role holding only `AUDIT_READ` scoped to Station A, after an Owner updates both Station A and Station B, saw Station A's event but not Station B's; an org-wide reader saw both.
2. **No self-service password change.** Added `PATCH /auth/password` (verifies current password, hashes the new one, revokes every other session, audit-logged). Verified: wrong current password → 401; correct change → old password stops working, new one works, and a second concurrently-logged-in session's refresh token is revoked by the change.
3. **No session visibility or bulk revocation ("I lost my device").** Added `GET /auth/sessions` (lists active, non-revoked, non-expired sessions by id/created_at/expires_at only — never the token itself) and `POST /auth/logout-all` (revokes every active session for the caller). Verified: two concurrent logins show as two sessions; `logout-all` revokes both, and the second session's refresh token is then rejected.

**Also explicitly tested (per the request) and confirmed correct, not just asserted:**
- Unauthorized access: `GET /organizations`, `GET /roles`, `GET /auth/me` without a token → `401` for all three.
- Cross-organization leakage: a user with a role only in org A never sees org B in `GET /organizations`; a user that exists only in org B never appears in org A's `GET .../users`; a station belonging only to org B never appears in org A's `GET .../stations`, and reading org B directly is a flat `403`.
- Cross-station leakage: covered by the audit fix above, plus the existing Phase 1 coverage of station-scoped station reads.
- Least-privilege review of seeded roles: Cashier/Operator has `station:read` only; Shift Supervisor adds `user:read`/`role:read`; Storekeeper/Technician has `station:read` only; only the seeded Owner role carries every permission including `user:assign_role` - no seeded role is over-permissioned relative to what Phase 1's feature set needs.

**New test files:** `tests/test_cross_tenant_isolation.py` (8 tests), `tests/test_sessions_and_password.py` (4 tests).

**Regression run:** `pytest tests/` → **49 passed, 0 failed** (37 going in, 12 new). Full `docker compose up --build backend` re-run after the schema change: migration `7f2f05f5b92b` applied automatically on container start, `/health` and `/ready` both correct.

**Not done (explicitly out of scope, not silently dropped):** no frontend UI for the new password/session endpoints yet — the request was about securing the backend, and the dashboard shell doesn't have a settings area yet to put them in. Rate limiting on `/auth/login` remains deferred to Phase G, as before.

**Core invariants enforced in code, not just documented:**
- Book stock is computed only by `app/core/stock.py::get_book_stock`, summing the ledger - never read from a mutable column.
- Capacity is checked **twice**: an early check at receipt creation (UX feedback) and an authoritative re-check at approval time against the then-current ledger, with the tank row locked (`SELECT ... FOR UPDATE`) across both checks so two receipts on the same tank can't both pass against the same stale figure.
- Approved/rejected receipts are terminal - every state transition re-fetches the receipt with a row lock and checks `status` before acting, so a duplicate or replayed approval/rejection/unload request is rejected (409), never double-applied.
- The ledger insert, the receipt's own status update, and its audit log entry are all in the one transaction that `approve_receipt` commits - they succeed or fail together.
- Fuel prices are genuinely append-only: no update endpoint exists at all; "current price" is always derived (`app/core/pricing.py::get_current_price`) from the full history, never a column that gets overwritten.

## Phase C — completion record (2026-10-28)

**Scope delivered:** opening/closing physical tank readings, opening/closing nozzle totalizers with explicit meter replacement/reset/rollover handling, exceptional litres (test draws/calibration), mid-shift price-change boundary-reading capture, the full shift open → close → approve lifecycle, and a live stock-variance report. Scoped out, and recorded above (not silently dropped): expected revenue and any shift reopen/correction workflow.

**New models:** `Shift` (+ `ShiftStatus`), `ShiftTankReading` (+ `TankReadingType`), `ShiftNozzleReading` (+ `MeterEventType`), `ShiftExceptionalEvent` (+ `ExceptionalEventType`), `ShiftPriceChange`, `ShiftPriceChangeReading`. `Station` gained `require_price_change_reading` (default `true`) and `shift_variance_tolerance_percent` (default 0.5%) - see `docs/ASSUMPTIONS.md` #6.

**New permissions:** `shift:read`, `shift:open`, `shift:close`, `shift:approve`. Per blueprint §12's explicit "Cashier / Nozzle Operator → shift submission and closure" mapping, Cashier/Operator gets `shift:open`+`shift:close` - the one place in this app where that role has a write permission beyond `station:read`. Approval (and meter-event approval) stays with Station Manager/Shift Supervisor/Owner, matching the separation-of-duties pattern already established for tanker receipts.

**Migrations:** `fb3e54164d78` (6 new tables + 2 new `Station` columns, hand-adjusted for the same existing-rows/`NOT NULL` reason as the Phase B `Station` migration).

**Core design decisions and why (also in `docs/ASSUMPTIONS.md`):**
- **`reading_type` is never a request-body field.** Opening and closing tank readings are two separate endpoints (`POST .../tank-readings/opening` vs `.../closing`) with separate permissions, specifically so permission resolution never depends on request-body content - the same lesson the Phase A QA pass learned the hard way for role assignment. This was caught by the live smoke test *before* it reached the test suite (see below).
- **Dispensed litres is computed and stored once, at the moment the closing reading is recorded** - not recomputed later - and a meter event's two segments are each independently validated non-negative before that happens.
- **A flagged meter event must be approved separately from the shift itself**, and the shift cannot be approved while one is outstanding - this is the "approved meter rollover/replacement/reset workflow" ARCHITECTURE.md already committed to; Phase C is what actually builds it.
- **Exceptional litres are posted as their own ledger entry (`TEST_CALIBRATION`), never netted silently into `SALE`.** Both decrease book stock identically; keeping them visibly separate is what makes the split auditable later.
- **A shift's book-stock variance figure is a projection from its own readings, not a ledger timestamp query** - the ledger posting happens at *approval* time, which is chronologically after `closed_at`, so querying "book stock as of closed_at" would always exclude the shift's own postings. This was a real bug, caught by the live smoke test, not by reading the code - see below.
- **Capacity/stock sufficiency is re-checked under a tank row lock at approval time**, mirroring the Phase B receipt pattern exactly, for the same concurrency reason.

**Live smoke test (run before the formal suite, to catch wiring bugs cheaply):** walked the full lifecycle over real HTTP - receipt → shift open → opening readings → closing readings → close → approve → variance report - then specifically exercised the meter-rollover path. Found and fixed two real defects this way:

**Core design decisions and why (also in `docs/ASSUMPTIONS.md`):**
- **Revenue and cash movements are computed by two structurally separate modules that never read each other's tables.** `app/core/revenue.py::compute_expected_fuel_revenue` reads only `ShiftNozzleReading`/`ShiftPriceChange`/`FuelPrice`; `app/core/reconciliation.py` reads only `ShiftTender`/`ShiftCashMovement`. This is what makes "a deposit never affects the revenue variance" a structural guarantee rather than a careful-coding promise, and it's verified directly by `test_deposit_reduces_expected_cash_but_never_affects_revenue_variance`.
- **A decreasing cash movement (expense/deposit/transfer-out/refund) must be individually approved before it can reduce expected physical cash**, and reconciliation creation is blocked outright while any are still pending - so an expense can never be silently counted once as "subtracted" and then disputed later with no record of who approved it.
- **Money is rounded exactly once**, after summing every unrounded litre-segment × price line item into a shift total - not per line item - a specific default, flagged as not an accounting determination (`docs/ASSUMPTIONS.md` #20).
- **An amendment is the only way to change an already-created reconciliation**, and only two fields are amendable (`actual_physical_cash`, `explanation`) - the derived figures (expected revenue, tender totals, expected cash) are never hand-edited; if one of those is wrong, the fix is to reverse and re-enter the underlying tender/movement, which then flows through as a new input. Approving an amendment recomputes every dependent figure but deliberately does not clear a prior authorization's `authorized_by`/`authorized_at` - that stays a true record of what was approved at the time (`docs/ASSUMPTIONS.md` #23).
- **Simple reversal (tenders, cash movements) is allowed regardless of shift status** and is excluded from every sum, rather than deleted - the original mis-entry stays visible in the audit trail.
- **Financial reconciliation is a precondition of final shift approval**, checked in `shifts.py::approve_shift` after the pre-existing meter-event-approval precondition (so a shift with both problems is told about the operational one first, since it's the earlier real-world step) and before the book-stock-sufficiency check.

3. `zoneinfo` had no tzdata source at all on this dev machine - added the `tzdata` package (pure data, explicitly for exactly this reliability reason) rather than leaving the station-timezone feature silently degrade to UTC wherever it's run.
4. The Daily Entry workspace's "Opening stock" card never actually rendered a closing-dip input, so a shift could never be closed - found by the real validation error this produced, not a code read.
5. Starting a new entry for a past, empty date silently created a shift dated *today* instead (the backend has no way to backdate `opened_at` - by design), leaving the page stuck. Fixed by only offering "start" for the station's actual today; a past empty date is now explained as needing a correction, not a new entry.
6. The Playwright suite's own selectors broke when `role="tab"` was correctly added for accessibility (an element's explicit ARIA role overrides its implicit one) - caught and fixed by re-running the suite, not assumed safe.

**New backend surface (small, additive, reusing existing patterns):**
- `GET /organizations/{org}/stations/{station}/shifts?business_date=YYYY-MM-DD` (new query param on the existing list endpoint).
- `GET /organizations/{org}/stations/{station}/nozzles` (new read-only overview endpoint - every nozzle at the station with its tank/fuel-grade context, current price, and last closing totalizer in one call; the per-dispenser CRUD endpoint is unchanged).
- No new tables, no new migration - both additions are read/filter logic over existing models.
